# Cryptography Tool Images, SEO, and Public Release Design

## Goal

Give the seven newly added encryption, encoding, and hashing tools a cohesive set of generated raster covers, make each tool independently shareable and discoverable, and publish the verified result to the public GitHub Pages site without including unrelated working-tree changes.

## Scope

The release covers these routes:

1. `/tools/vigenere-cipher/`
2. `/tools/affine-cipher/`
3. `/tools/transposition-cipher/`
4. `/tools/playfair-cipher/`
5. `/tools/hill-cipher/`
6. `/tools/hash-generator/`
7. `/tools/aes-hex-calculator/`

The abandoned navigation exploration is out of scope. ROT Explorer already predates this tool set and will retain its existing cover.

## Image direction

Use a consistent **cryptography instruments** art direction: dark graphite workbench surfaces, restrained brass/gold mechanisms, cool steel details, precise studio lighting, and an engineered rather than fantasy aesthetic. The images should feel like physical instruments that visualize the algorithm.

All images will:

- use a landscape composition that crops safely to 16:9;
- avoid embedded titles, labels, logos, watermarks, random code, and illegible glyphs;
- reserve the outer edges as low-detail safe zones for responsive cropping;
- use the existing charcoal, muted blue, and gold design language;
- remain understandable at small card size;
- be generated as raster artwork, then optimized through the existing AVIF/WebP pipeline.

### Individual concepts

- **Vigenère & Autokey:** paired alphabet rotors with a brass key ribbon advancing through the mechanism.
- **Affine cipher:** a modular transformation console with separate multiply and shift dials feeding one output track.
- **Rail Fence & Transposition:** letter-like neutral tiles moving across zigzag rails and reordered columns; no readable fake text.
- **Playfair:** a precise 5-by-5 brass-and-graphite tile board with paired tokens and a highlighted rectangle relationship.
- **Hill cipher:** luminous vector blocks passing through a physical matrix frame into transformed output blocks.
- **Hash generator:** an input stream compressed through a one-way mechanical chamber into a fixed-length fingerprint pattern.
- **AES hex calculator:** a 4-by-4 byte-grid instrument passing through four distinct transformation stages, presented as a secure laboratory mechanism rather than a padlock cliché.

## Product integration

Each generated source image will live under `public/media/tools/design/` with a stable, descriptive `-v2.png` filename. The seven entries in `data/calculator-visuals.js` will switch from the current dark/light SVG pair to the new single raster image. The existing SVG files remain in the repository as prior assets and fallback references; they are not deleted.

`PublicImage` will serve the optimized responsive variants generated by `npm run prepare:images`. The image pipeline's cover budget remains 180 KB per generated AVIF/WebP variant.

## SEO integration

Each route already has a unique search title, meta description, direct answer, FAQ content, WebApplication schema, canonical URL, and sitemap entry. This work will preserve and verify those contracts, then add the route's own generated cover to:

- Open Graph `images` metadata;
- Twitter `summary_large_image` metadata;
- the WebApplication structured-data `image` field where the shared schema component can accept it without changing unrelated routes.

The metadata must use absolute production URLs and meaningful image alt text derived from the tool title. No keyword stuffing or duplicate titles will be introduced.

## Verification

Before publication:

1. Inspect all seven generated images for visual consistency, algorithm relevance, safe cropping, and absence of unwanted text or watermarks.
2. Run the responsive image pipeline and confirm there are no missing or oversized referenced images.
3. Run focused visual-registry, metadata, schema, sitemap, and browser-route tests for the seven tools.
4. Run the SEO suite, content validation, and production build.
5. Run the repository test suite and compare any failures with the recorded baseline; do not describe the suite as green if baseline failures remain.
6. Inspect representative desktop and mobile screenshots in dark and light themes.

## Release method

The source branch and public branch have different roles:

- `source` contains the Next.js application.
- `main` contains the exported GitHub Pages artifact and is the repository's public Pages branch.

The release will commit only files created or intentionally modified for this scope. Existing unrelated dirty files will not be staged. After verification, push the source commits to `origin/source`, build the static export, copy that verified export into a clean deployment worktree based on the current `origin/main`, commit the generated site, and push that deployment commit to `origin/main`.

Because publishing changes external state, deployment will occur only after the local source commit and verification evidence are complete. The final report will include both source and deployment commit identifiers and the public URL.

## Acceptance criteria

- All seven routes display distinct generated covers that share one intentional art direction.
- The covers are responsive and use generated AVIF/WebP variants within the existing budget.
- Every route has a canonical URL, unique title and description, share image, WebApplication schema, and sitemap inclusion.
- Scoped tests, SEO tests, content validation, and production build pass.
- No unrelated dirty changes are committed or published.
- The verified static site is pushed to the public Pages branch.
