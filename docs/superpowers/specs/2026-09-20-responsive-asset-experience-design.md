# Responsive Asset Experience Design

**Date:** 2026-09-20  
**Status:** Approved for planning  
**Scope:** Image and visual-asset delivery across the portfolio, with dedicated simplified mobile artwork for tools. Tool interaction redesign is explicitly deferred.

## Objective

Make every image-led surface feel intentional on phones, tablets, laptops, desktop monitors, ultrawide displays, and high-density screens. Visitors should receive an appropriately sized asset instead of downloading a desktop source, while tool artwork must remain understandable at phone-card size rather than becoming a miniature technical diagram.

Success means:

- every raster image that is actually referenced by the site participates in the responsive image pipeline;
- each responsive image has modern AVIF and WebP outputs plus its original fallback;
- browsers can select a suitable intrinsic width using `srcset` and an accurate `sizes` hint;
- tool covers that lose meaning when reduced have a separate, simplified mobile composition;
- desktop and wide-screen artwork preserves useful detail rather than stretching a phone asset;
- image dimensions are always known, avoiding layout shift;
- missing, oversized, unregistered, or incorrectly wired assets fail automated checks;
- the initial mobile payload is materially smaller without reducing desktop quality.

## Chosen Approach

Use a hybrid system rather than one universal crop or a completely separate image library for every breakpoint.

1. **Mechanical responsive variants for every used raster.** The existing pipeline expands to discover and process the entire referenced raster inventory, not only its current allowlist. Each source produces bounded variants at widths appropriate to its own dimensions.
2. **Art-directed mobile variants for tool covers.** Tool covers receive a dedicated portrait-friendly or compact landscape composition only where ordinary scaling makes the concept difficult to read. These are genuine simplified assets, not arbitrary center crops.
3. **One reusable rendering API.** `PublicImage` accepts optional mobile and wide art-direction sources while retaining the current single-source API. It produces a standards-based `<picture>` with media-specific sources.
4. **Auditable asset roles.** A small registry records the role, crop policy, focal point, mobile source, wide source, and intended `sizes` preset. This prevents CSS and component code from guessing.

This gives the broad performance benefit of automation while reserving generation effort for visuals where comprehension genuinely improves.

## Asset Inventory and Classification

The pipeline will inventory referenced files from `app`, `components`, `content`, `data`, and `lib`, plus explicit sources used through data indirection. Generated responsive output is excluded from source discovery.

Each referenced raster receives one role:

- **tool-cover:** conceptual artwork displayed in tool catalogs and related-tool cards;
- **project-cover:** portfolio cover or project evidence preview;
- **gallery-evidence:** photographs, certificates, screenshots, or build documentation;
- **portrait:** profile photography;
- **tutorial-cover:** lesson or workshop imagery;
- **social:** Open Graph and Twitter preview assets;
- **interface-screenshot:** real application UI that must not be regenerated by AI;
- **decorative:** non-content imagery with empty alternative text.

The audit must report referenced sources, unreferenced candidates, direct `<img>` usage, dimensions, byte size, and responsive coverage. Unreferenced files are reported but not deleted in this project.

## Responsive Variant Matrix

Responsive generation is bounded by source dimensions; images are never enlarged merely to fill a matrix.

| Target | Nominal widths | Primary use |
|---|---:|---|
| Compact phone | 240, 320, 480 | result cards, narrow tool cards, compact galleries |
| Large phone / small tablet | 640, 768 | full-width mobile content and two-column tablet cards |
| Tablet / laptop | 960, 1280 | page features, project covers, desktop cards |
| Desktop / wide | 1600, 1920, 2560 when the source supports it | wide feature artwork and high-density displays |

AVIF and WebP variants are generated for each useful width. The original remains the final fallback. Variant widths are chosen per role so small icons do not create pointless large files and evidence photography can retain enough detail for large screens.

Initial per-file budgets:

- tool and tutorial card variants: 120 KB;
- portraits: 100 KB;
- project covers and interface screenshots: 180 KB;
- evidence and gallery photography: 260 KB;
- wide hero variants: 320 KB;
- social preview files: 300 KB.

The encoder reduces quality only to the defined floor and reports any file that still exceeds budget. It does not silently produce visibly damaged output.

## Tool-Cover Art Direction

Tool covers are judged by comprehension at approximately 320 CSS pixels wide. A mobile cover must communicate one idea in under two seconds.

### Mobile composition rules

- one input, one transformation, one output;
- no small formulas, legends, tick labels, paragraphs, or decorative machinery;
- no generated text inside the bitmap;
- the key object occupies roughly 55–70% of the frame;
- strong silhouette, high contrast, and generous negative space;
- essential labels remain semantic HTML overlays where needed;
- consistent ASL charcoal, blue/cyan, and gold palette;
- safe focal area centered for narrow cards and flexible cropping.

### Desktop and wide composition rules

- retain the current richer engineering detail where it helps explain the tool;
- add breathing room rather than scaling objects until they become oversized;
- use 16:9 as the default tool-cover ratio;
- generate a wider composition only when an actual wide placement exists;
- never use AI-generated substitutes for screenshots of real interfaces.

### Prioritization

All tool-cover sources receive responsive encoded widths. Dedicated generated mobile compositions are created first for the tool families with dense diagrams or multi-stage concepts: cryptography and hashing, satellite and RF, circuit diagrams, number-system visuals, advanced workbench covers, and any remaining cover that fails the 320-pixel comprehension review.

Simple photographic or already minimal covers use focal cropping rather than unnecessary regeneration.

## Rendering API

`PublicImage` remains the only general raster renderer. Its extended contract supports:

- `src`: required default source;
- `mobileSrc`: optional simplified source selected below the mobile breakpoint;
- `wideSrc`: optional wide composition selected above the wide breakpoint;
- `sizes`: explicit responsive layout hint;
- existing native image attributes such as `alt`, `loading`, `fetchPriority`, and `decoding`.

The component renders media-specific AVIF and WebP sources in specificity order, followed by the default responsive sources and original fallback. Width and height come from the manifest. The component must preserve the source aspect ratio and must not cause cumulative layout shift.

Reusable `sizes` presets will cover full-bleed features, three-column tool cards, two-column cards, article media, galleries, and portraits. Call sites can still provide a precise string when a layout does not match a preset.

## Pipeline and Registry

The generated manifest expands from a flat source map to records that can represent an art-directed family. A human-authored registry supplies only information automation cannot infer:

- asset role;
- optional mobile and wide source;
- focal position for mechanical crop previews;
- sizes preset;
- decorative/content status.

The build pipeline will:

1. discover referenced raster sources and registry sources;
2. validate that all configured files exist and decode;
3. read dimensions and classify roles;
4. generate useful widths in AVIF and WebP;
5. enforce byte budgets;
6. emit the typed manifest and a machine-readable audit report;
7. fail checks for missing files, oversized output, missing dimensions, or a referenced raster that bypasses the responsive system without an explicit exemption.

Incremental generation remains modification-time aware so normal builds do not re-encode unchanged files.

## UX and Accessibility Requirements

- meaningful images retain concise, specific alternative text;
- decorative artwork uses empty alternative text and never repeats nearby headings;
- tool concepts conveyed by color also have semantic HTML labels or written descriptions;
- below-the-fold media remains lazy-loaded;
- likely largest-contentful-paint images can opt into eager loading and high fetch priority;
- object positioning is explicit when cropping is possible;
- mobile artwork is not hidden after both desktop and mobile files are downloaded—the browser must select through `<picture>` before fetching;
- reduced-motion preferences remain respected by surrounding interactive visuals.

## SEO Requirements

- image URLs remain stable when the visual meaning is unchanged;
- generated variants are delivery assets and do not become canonical content URLs;
- primary source filenames remain descriptive;
- Open Graph and Twitter assets keep their required 1200×630-style presentation and absolute metadata URLs;
- every indexable image-led page keeps useful alternative text and intrinsic dimensions;
- the image audit is included in release verification alongside existing SEO tests.

## Testing and Visual Verification

Automated tests will cover:

- discovery of every referenced raster;
- generated formats and widths for each role;
- byte budgets and decodability;
- correct `<picture>` media ordering for mobile/default/wide sources;
- original fallback presence;
- explicit intrinsic dimensions;
- prevention of unapproved direct `<img>` usage;
- mobile art-direction mapping for every selected tool cover;
- no upscaling past source width;
- stable source and variant paths.

Browser verification will sample phone, tablet, laptop, desktop, and ultrawide viewports. The review checks crop quality, concept readability, layout shift, pixelation, visual weight, and whether the network selects the expected asset family. Representative pages include the Tools hub, text and encoding category, satellite and RF categories, tool detail pages, Work hub, project detail pages, About, and Publications.

## Delivery Sequence

1. Produce the full asset inventory and close discovery gaps.
2. Extend the pipeline, manifest, registry, and rendering component.
3. Migrate every meaningful raster call site to the responsive renderer.
4. Generate and integrate simplified mobile tool covers in family batches.
5. Generate any genuinely necessary wide variants; avoid redundant artwork.
6. Run image, accessibility, SEO, build, and regression verification.
7. Compare mobile payload and visual screenshots against the current public release.
8. Commit source changes and publish the static export only after verification.

## Out of Scope for This Phase

- restructuring calculator controls or result layouts;
- rebuilding Gradify’s mobile workflow;
- rewriting tool calculation engines;
- deleting historical or unreferenced media;
- replacing authentic project photographs or UI screenshots with generated imagery;
- introducing a third-party image CDN.

Those interaction changes can follow once the shared asset system is stable.

## Acceptance Criteria

- all referenced raster assets are accounted for by the responsive pipeline or an explicit, justified exemption;
- all responsive outputs decode and remain inside their role budget;
- selected dense tool families have dedicated mobile assets and render them only at the intended breakpoint;
- phone, tablet, laptop, desktop, and ultrawide samples show no broken crops, pixelation, overflow, or layout shift attributable to images;
- the production build, SEO suite, focused asset tests, and existing regression comparison complete without a new failure;
- the public deployment serves the new assets and live `<picture>` selection behaves as designed.
